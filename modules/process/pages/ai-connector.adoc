= AI connectors
:page-aliases: ROOT:ai-connector.adoc
:description: Bonitasoft now offers AI connectors that let you seamlessly integrate advanced language models like OpenAI, Mistral, Anthropic Claude, Azure OpenAI, Gemini, Cohere, DeepSeek, and Groq into your business processes.

{description} These connectors support three powerful use cases:

- Generate text content from custom prompts
- Classify documents into predefined categories
- Extract structured data from unstructured text or images

By securely sending data from your processes to LLMs over HTTPS, you can enhance automation, improve decision-making, and streamline information handling—all without writing custom code.


The Bonita AI Connectors are available for **Bonita 10.2 Community (2024.3)** version and above.

image::ai-connectors.png[AI Connectors flux]

== Getting started

To use a connector, add it as an extension dependency to your Bonita project. Choose the one related to your AI provider.

Currently supported providers:

* image:openai.png[OpenAI] OpenAI
* image:mistral.png[MistralAI] Mistral AI
* image:anthropic.png[Anthropic] Anthropic (Claude)
* image:azure-openai.png[Azure OpenAI] Azure OpenAI
* image:gemini.png[Gemini] Google Gemini [BETA]
* image:cohere.png[Cohere] Cohere [BETA]
* image:deepseek.png[DeepSeek] DeepSeek [BETA]
* image:groq.png[Groq] Groq [BETA]

WARNING: Image documents are not supported yet for Mistral connector due to a limitation of the underlying library we use.

NOTE: The Anthropic and Azure OpenAI connectors were added in version 1.3.0 of the AI connector extension.

NOTE: Gemini, Cohere, DeepSeek, and Groq connectors were added in version 1.1.1 of the AI connector extension.

=== Common configuration

[caption=Configuration]
|===
|Parameter name |Required |Description |Default value

|*apiKey*
|false
a|The AI provider API key. Parameter is optional for testing purpose but obviously required with official OpenAI endpoint. 

The connector will look for API key value in this order: 

- A system environment variable named `AI_API_KEY` 
- A JVM property named `AI_API_KEY` (`-DAI_API_KEY=xxx`) 
- the provided connector `apiKey` parameter 
 
And at last it will use a dummy default `changeMe` value if no other value found. 
| changeMe

|*url*
|false
|The AI provider endpoint URL. This parameter allows to use an alternate endpoint for tests. For Azure OpenAI, this must be your Azure OpenAI resource endpoint (e.g., `\https://myresource.openai.azure.com`).
|Default to the official provider endpoint if not specified.

|*requestTimeout*
|false
|The request timeout in milliseconds for OpenAI calls.
|null

|*chatModelName*
|false
a|The model to use for chat like `gpt-4o`, `gpt-4o-mini`, `llama`, `pixtral`, `claude-sonnet-4-20250514`, ... See respective documentation for detailed information about models.

- OpenAI : https://platform.openai.com/docs/models/models
- Mistral AI : https://docs.mistral.ai/getting-started/models/models_overview
- Anthropic : https://docs.anthropic.com/en/docs/about-claude/models
- Azure OpenAI : https://learn.microsoft.com/en-us/azure/ai-services/openai/concepts/models
- Gemini : https://ai.google.dev/gemini-api/docs/models/gemini
- Cohere : https://docs.cohere.com/docs/models
- DeepSeek : https://platform.deepseek.com/api-docs
- Groq : https://console.groq.com/docs/models
a|
- OpenAI : `gpt-4o`
- MistralAI : `pixtral-12b-2409`
- Anthropic : `claude-sonnet-4-20250514`
- Azure OpenAI : deployment name (configured in Azure Portal)
- Gemini : `gemini-2.0-flash`
- Cohere : `command-r-plus`
- DeepSeek : `deepseek-chat`
- Groq : `llama-3.3-70b-versatile`

|*modelTemperature*
|false
a|The temperature to use for the model. Higher values will result in more creative responses. Must be between `0` and `1`. 

Leave blank if the selected model does not support this parameter. 

If the parameter is not present, the temperature will not be set in chat context.
|null
|===

== Connectors

AI connectors have the capability to return structured data in JSON format. It is possible to pass a https://json-schema.org/learn/getting-started-step-by-step[JSON schema] to tell the LLM how to format response data. 

When using a JSON schema, you **must** list in the `required` property, all the fields you want in the JSON response. 

.JSON schema sample
[source, json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "ProofOfAddress",
  "type": "object",
  "required": [
    "firstName",
    "lastName",
    "fullName",
    "fullAddress",
    "emissionDate",
    "issuerName",
    "identificationNumber"
  ],
  "properties": {
    "firstName": {
      "type": "string"
    },
    "lastName": {
      "type": "string"
    },
    "fullName": {
      "type": "string"
    },
    "fullAddress": {
      "type": "string"
    },
    "emissionDate": {
      "type": "string"
    },
    "issuerName": {
      "type": "string"
    },
    "identificationNumber": {
      "type": "string"
    }
  }
}
----

=== Ask connector

Take a user prompt and send it to OpenAI then return the AI response. The prompt text can ask question about a provided process document.

[caption=Configuration]
|===
|Parameter name |Required |Description |Default value

|*systemPrompt*
|false
|The system prompt to pass to the OpenAI endpoint.  It helps to influence the behavior of the assistant and specify a default context. (ex: You are a personal finance advisor, providing guidance, etc.)
|"You are a polite Assistant"

|*userPrompt*
|*true*
|The user prompt content to send to the AI provider
|

|*sourceDocumentRef*
|false
a|The reference to the process document to load and add to the user prompt. 

If not null, the connector will try to read the specified document and send it as an attachment to the user prompt. Supported formats are "doc", "docx", "pdf", ... (see https://tika.apache.org/3.1.0/formats.html)
|null

|*outputJsonSchema*
|false
|The JSON schema that represent how to structure the JSON connector output.
|null

|===

The result can be a simple JSON object or one compliant with a provided JSON schema.
This result will be placed as a map entry of type `java.lang.String` for the key named *output*.

=== Extract connector

This connector allow extracting information from a bonita document.

[caption=Configuration]
|===
|Parameter name |Required |Description |Default value

|*sourceDocumentRef*
|*true*
a|The reference to the process document to load and add to the user prompt. 

If not null, the connector will try to read the specified document  and send it as an attachment to the user prompt. Supported formats are "doc", "docx", "pdf", ... (see https://tika.apache.org/3.1.0/formats.html)
|null

|*fieldsToExtract*
|false
a|The list of fields to extract from the given document. 

The connector expect a list of String (like `firstName`, `lastName`, `address`).
|null

|*outputJsonSchema*
|false
a|The JSON schema that represent how to structure the JSON connector output. 

If a JSON schema is specified, the `fieldsToExtract` parameter is ignored.
|null

|===

IMPORTANT: You must provide at least one of `fieldsToExtract` or `outputJsonSchema` parameters.

The result can be a simple JSON object or one compliant with a provided JSON schema.
This connector result will be placed as a map entry of type `java.lang.String` for the key named *output*.

=== Classify connector

This connector allows classifying a bonita process document according to a list of categories provided by the user.

[caption=Configuration]
|===
|Parameter name |Required |Description |Default value

|*sourceDocumentRef*
|*true*
a|The reference to the process document to load and add to the user prompt. 

If not null, the connector will try to read the specified document and to send it as an attachment to the user prompt. Supported formats are "doc", "docx", "pdf", ... (see https://tika.apache.org/3.1.0/formats.html)
|null

|*categories*
|*true*
a|The list of categories used to classify the given document. 

The connector expect a list of String (like `RIB`, `ID`, ...).
It is recommended to add a default category if none other matches such as `Unknown`
|null

|===


The result is a JSON String such as the following sample.

.sample classification result
[source,json]
----
{
  "category": "xxx",
  "confidence": 0.9
}
----

The confidence score is defined as :

- [0.0..0.3]: Very uncertain or guessing
- [0.3..0.6]: Some uncertainty, potential ambiguity exists
- [0.6..0.8]: Reasonably certain, minor doubt
- [0.8..1.0]: Very certain, no doubt

This connector result will be placed as a map entry of type `java.lang.String` for the key named *output*.

== Provider-specific configuration

The AI connectors support multiple providers. Each provider requires its own connector JAR and may have specific configuration requirements.

=== OpenAI

[caption=OpenAI configuration]
|===
|Parameter |Value

|*Connector module*
|`bonita-connector-ai-openai`

|*Default model*
|`gpt-4o`

|*API endpoint*
|`++https://api.openai.com/v1++`

|*API key source*
|https://platform.openai.com/api-keys[OpenAI API Keys]
|===

.Example: Summarize a customer complaint
[source,json]
----
{
  "apiKey": "${AI_API_KEY}",
  "chatModelName": "gpt-4o",
  "systemPrompt": "You are a customer service analyst. Summarize complaints into structured reports.",
  "userPrompt": "Summarize this complaint and suggest a resolution: ${complaintText}",
  "outputJsonSchema": "{\"type\":\"object\",\"required\":[\"summary\",\"category\",\"suggestedResolution\",\"priority\"],\"properties\":{\"summary\":{\"type\":\"string\"},\"category\":{\"type\":\"string\"},\"suggestedResolution\":{\"type\":\"string\"},\"priority\":{\"type\":\"string\"}}}"
}
----

.Example: Extract structured data from a contract
[source,json]
----
{
  "apiKey": "${AI_API_KEY}",
  "chatModelName": "gpt-4o",
  "fieldsToExtract": "contractNumber,parties,startDate,endDate,totalValue,currency"
}
----

=== Azure OpenAI

[caption=Azure OpenAI configuration]
|===
|Parameter |Value

|*Connector module*
|`bonita-connector-ai-openai` (with custom URL)

|*Default model*
|Depends on your Azure deployment name

|*API endpoint*
|`++https://<your-resource>.openai.azure.com/openai/deployments/<deployment-name>++`

|*API key source*
|Azure Portal > Cognitive Services > Keys
|===

To use Azure OpenAI, configure the *url* parameter with your Azure endpoint and use the *chatModelName* matching your deployment name.

.Example: Azure OpenAI configuration
[source,json]
----
{
  "apiKey": "${AZURE_OPENAI_API_KEY}",
  "url": "https://my-company.openai.azure.com/openai/deployments/gpt-4o",
  "chatModelName": "gpt-4o",
  "systemPrompt": "You are a helpful assistant for HR processes.",
  "userPrompt": "Evaluate this CV against the job description and provide a fit score: ${cvText}"
}
----

NOTE: Azure OpenAI uses the same OpenAI connector module but requires setting the `url` parameter to your Azure endpoint. API versioning is handled automatically.

=== Ollama (local models)

[caption=Ollama configuration]
|===
|Parameter |Value

|*Connector module*
|`bonita-connector-ai-openai` (with custom URL)

|*Default model*
|Depends on your local setup (e.g., `llama3`, `mistral`)

|*API endpoint*
|`++http://localhost:11434/v1++`

|*API key source*
|Not required (use any non-empty value)
|===

Ollama provides a local, OpenAI-compatible API. Use the OpenAI connector module with a custom URL pointing to your Ollama instance.

.Example: Ollama local model configuration
[source,json]
----
{
  "apiKey": "not-needed",
  "url": "http://localhost:11434/v1",
  "chatModelName": "llama3",
  "systemPrompt": "You are a document analysis assistant.",
  "userPrompt": "Extract the key dates and amounts from this invoice."
}
----

NOTE: Ollama runs entirely on-premises, making it suitable for sensitive data that cannot leave the organization's network. Ensure sufficient GPU/CPU resources for acceptable response times.

== Use cases

=== Classify incoming documents automatically

Add a *Classify* connector to a service task after document upload:

[source,json]
----
{
  "apiKey": "${AI_API_KEY}",
  "chatModelName": "gpt-4o",
  "categories": "INVOICE,CONTRACT,ID_CARD,PROOF_OF_ADDRESS,OTHER"
}
----

Use the result in an exclusive gateway to route the process based on the document type:

* `category == "INVOICE"` -> Invoice processing lane
* `category == "CONTRACT"` -> Legal review lane
* `category == "ID_CARD"` -> Identity verification lane

=== Extract structured data from documents

Use *Extract* to populate BDM fields automatically from uploaded documents:

[source,json]
----
{
  "apiKey": "${AI_API_KEY}",
  "chatModelName": "gpt-4o",
  "fieldsToExtract": "invoiceNumber,issuerName,totalAmount,currency,dueDate,lineItems"
}
----

Then parse the JSON output to populate your business data model variables.

=== Generate responses with structured output

Use *Ask* with a JSON schema to generate structured content that can be directly mapped to process variables:

[source,json]
----
{
  "apiKey": "${AI_API_KEY}",
  "chatModelName": "gpt-4o",
  "systemPrompt": "You are a professional email writer.",
  "userPrompt": "Write a follow-up email for customer ${customerName} regarding case #${caseId}. The issue was: ${issueDescription}. It has been resolved.",
  "outputJsonSchema": "{\"type\":\"object\",\"required\":[\"subject\",\"body\"],\"properties\":{\"subject\":{\"type\":\"string\"},\"body\":{\"type\":\"string\"}}}"
}
----

=== Multi-document analysis

Use *Ask* with multiple source document references to compare or cross-reference documents:

[source,json]
----
{
  "apiKey": "${AI_API_KEY}",
  "chatModelName": "gpt-4o",
  "systemPrompt": "You are a financial auditor.",
  "userPrompt": "Compare these two invoices and identify any discrepancies in amounts, dates, or line items.",
  "sourceDocumentRefs": ["invoice_v1", "invoice_v2"]
}
----

== Choosing the right provider

|===
|Criteria |Recommended Provider |Why

|Best general-purpose reasoning
|OpenAI (`gpt-4o`) or Anthropic (`claude-sonnet-4-20250514`)
|Strong at complex analysis, extraction, and generation

|Cost-sensitive batch processing
|Mistral (`mistral-large-latest`) or Gemini (`gemini-2.0-flash`)
|Lower cost per token with good quality

|Data sovereignty / on-premises
|Ollama (local)
|Data never leaves your infrastructure

|Enterprise compliance (Azure AD)
|Azure OpenAI
|Integrates with existing Azure security policies

|Fast classification and routing
|Gemini (`gemini-2.0-flash`)
|Very low latency, good accuracy

|Document understanding with images
|OpenAI (`gpt-4o`) or Gemini (`gemini-1.5-pro`)
|Native multimodal support
|===
